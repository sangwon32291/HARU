# HARU — 4인 역할 분담표 (프론트엔드 2 / 백엔드 2)

> 문서 버전 v1.0 / 2026-10-20

## 0. 이 문서의 성격

- 아래 배정은 **담당 영역**이다. 각자 자기 영역의 코드를 이해하고, 수정하고, 발표에서 설명할 수 있어야 한다.
- 파일 경로가 곧 경계선이다. **자기 담당 파일만 수정**하고, 공용 파일은 합의 후 변경한다.
- 코드량은 균형을 보기 위한 참고치이며, 난이도와 남은 작업량이 더 중요하다.

## 1. 한눈에 보기

```
┌─────────────────── 프론트엔드 (화면) ───────────────────┐
│  팀원 1  지도 · 탐색 · 공통 UI        src/components/  │
│  팀원 2  거래 · 커뮤니티 · 마이페이지  src/pages/       │
└────────────────────────────────────────────────────────┘
                          ↕  서비스 함수 호출 (경계면)
┌─────────────────── 백엔드 (데이터·권한) ───────────────┐
│  팀원 3  스키마 · 인증 · 공고/지원     src/services/    │
│  팀원 4  권한(RLS) · 리뷰 · 커뮤니티   supabase/        │
└────────────────────────────────────────────────────────┘
```

**경계 규칙**: 프론트는 `src/services/*.ts`의 함수만 호출한다. 화면 코드에서 DB를 직접 건드리지 않는다. 백엔드는 함수 시그니처를 바꿀 때 반드시 프론트 담당과 합의한다.

| 담당 | 구분 | 한 줄 요약 | 현재 코드 | 남은 작업 |
|---|---|---|---|---|
| 팀원 1 | 프론트엔드 | 지도를 만들고 일자리를 찾게 한다 | 약 2,475줄 | 반응형 점검, 지도 개선 |
| 팀원 2 | 프론트엔드 | 지원하고 후기 쓰는 모든 화면 | 약 2,740줄 | UI 다듬기, 빈 상태 점검 |
| 팀원 3 | 백엔드 | 데이터 구조와 거래 로직 | 약 1,698줄 | 스키마 SQL, 인증 연동 |
| 팀원 4 | 백엔드 | 권한 검증과 신뢰도 로직 | 약 611줄 | **RLS 정책 전체**, 시드 SQL |

> 팀원 4의 현재 코드량이 적은 이유: RLS 권한 정책(`002_policies.sql`)이 아직 미작성이며, 이것이 남은 작업 중 가장 까다롭다. 완료 시점에는 균형이 맞는다.

- **Q. 그럼 도로는 어디서 왔나?** → 배경 타일만 OpenStreetMap 오픈 데이터. 투영·클러스터링·거리 계산은 `HaruMap.tsx`의 자체 코드. 타일 주소는 `TILE_URL` 한 줄이라 다른 지도로 교체 가능.
- **Q. 마커가 많으면 느려지지 않나?** → 화면 밖 마커는 제외하고, 격자 단위로 묶어 렌더링 수를 줄임.

### 구체적으로 한 작업

- **데이터 모델 설계** — 8개 테이블의 컬럼·타입·제약·인덱스 정의, Mermaid ERD 작성
- **상태값 규약 통일** — 4명이 다른 문자열을 쓰지 않도록 `enums.ts` 한 곳에서 정의. DB CHECK 제약과 1:1 대응
- **근접 검색 구현** — Haversine 공식으로 거리 계산, 반경 필터 + 거리순/급여순/최신순 정렬. **화면에서 거리를 다시 계산하지 않도록** 데이터 계층이 `distanceM`을 내려줌
- **상태 전이 규칙** — `ALLOWED_TRANSITIONS` 표로 허용 경로만 통과시킴 (예: 거절된 지원을 승인으로 되돌릴 수 없음)
- **중복 지원 차단** — 저장 직전 재확인 + DB UNIQUE 제약 2중 방어
- **평균 평점 집계** — 후기 등록·수정·삭제·숨김 시 업체 평점을 자동 재계산 (DB 트리거와 동일 동작)
- **오류 처리 체계** — 예외를 던지지 않고 `Result<T>`로 반환. 오류 코드 20종에 한국어 메시지 매핑
- **샘플 데이터 생성기** — 결정적 난수를 써서 새로고침해도 같은 데이터 생성

### 남은 작업

- `supabase/migrations/001_schema.sql` — 테이블·인덱스·트리거
- `src/services/supabase/` — 인증·공고·지원 어댑터 (함수 시그니처 유지)

### 발표 예상 질문

- **Q. 거리순 정렬을 어떻게 하나?** → Haversine 공식으로 대권 거리를 구함. Supabase 전환 시 PostGIS `st_distance`가 동일 역할을 하고, 공간 인덱스(GIST)로 가속됨.
- **Q. 왜 `Result<T>`를 쓰나?** → 예외를 던지면 호출부마다 try-catch가 흩어짐. 오류 코드를 타입으로 강제해 화면에서 빠뜨릴 수 없게 함.
- **Q. 상태값을 왜 한 파일에 모았나?** → 4명이 각자 `'승인됨'`, `'accepted'`, `'APPROVED'`를 쓰면 통합 시 전부 깨짐.

### 구체적으로 한 작업

- **후기 작성 권한 검증 (HARU 핵심 차별화)** — 지원 건의 상태가 `completed`일 때만 작성 허용. 프론트에서 버튼을 숨기는 것과 **별개로 데이터 계층에서 차단**
- **1지원 1후기 강제** — `application_id` UNIQUE로 중복 작성 차단
- **권한 매트릭스 구현** — 비로그인/로그인/작성자/구인자/관리자 5단계. 타인 공고의 지원자 목록 조회 차단, 본인 공고 지원 차단
- **관리자 권한 상승 차단** — 사용자가 스스로 `role`을 `admin`으로 바꾸지 못하도록 설계 (DB 트리거로 최종 차단)
- **신고 시스템** — 공고·후기·게시글·댓글 4종을 하나의 테이블로 처리(다형 참조), 중복 신고 차단
- **콘텐츠 숨김** — 숨긴 후기는 평균 평점 계산에서 자동 제외
- **세션 관리** — 새로고침 후에도 로그인 유지

### 남은 작업 (가장 중요)

- `supabase/migrations/002_policies.sql` — **RLS 정책 전체**. 8개 테이블 × 4개 동작(SELECT/INSERT/UPDATE/DELETE)
- 핵심 정책: 후기 INSERT 시 "해당 지원 건이 본인 것이고 상태가 completed인가"를 DB가 직접 검사
- `supabase/seed.sql` — 샘플 데이터 적재

### 발표 예상 질문

- **Q. 실제 근무자만 후기를 쓸 수 있다는 걸 어떻게 보장하나?** → 3중 방어. ① 화면에서 버튼 숨김(편의) ② 서비스 계층에서 상태 검증 ③ **DB의 RLS 정책**. ③이 최종 방어선이며, 개발자도구로 요청을 조작해도 뚫리지 않음.
- **Q. 프론트에서 버튼만 숨기면 안 되나?** → 안 됨. 브라우저 개발자도구로 직접 요청을 보낼 수 있음. 그래서 DB에서 검증함.
- **Q. 관리자 권한은 어떻게 막나?** → 사용자가 자기 프로필을 수정할 수 있으므로 `role` 컬럼 변경을 트리거로 감지해 차단.

| `package.json` | 전원 | 라이브러리 추가는 반드시 공지 |

**원칙**: 공용 파일은 **추가는 자유, 변경·삭제는 합의**. 기존 항목을 바꿔야 하면 단톡방에 먼저 올린다.

## 7. Git 브랜치

```
main                      배포용. 직접 커밋 금지
└─ develop                통합 브랜치
   ├─ feat/front-explore    팀원 1
   ├─ feat/front-trade      팀원 2
   ├─ feat/back-core        팀원 3
   └─ feat/back-auth        팀원 4
```

- 커밋 메시지: `feat: 공고 필터 추가` / `fix: 거리 계산 오류 수정` / `docs:` / `style:` / `refactor:`
- PR은 `develop`으로. 리뷰어 1명 이상 승인 후 머지
- 충돌 시: 공용 파일이면 소유자에게 문의, 자기 파일이면 본인이 해결
- `.env`는 **절대 커밋하지 않음**. 내용만 메신저로 공유
